## 구현 결과 (2026-11-04)

- 파일: `worklog/people.py`(사람·권한), `member_flow.py`(처음 등록·별칭·권한 카드), `worklog/stages.py`(게이트·제안·답), `confirm_flow.py`(메인 카드), `main.py`(메뉴·감지).
- 권한: `people.can_approve` 하나(관리자·개발 역할·권한을 받은 사람). 관리자 명령 '권한'으로 권한 주기·회수, 관리자 추가. 권한 없는 팀원에게는 되돌리기·삭제 확인·단계 답·소스 추가 버튼이 안 보인다.
- 처음 등록: 메뉴·버튼을 처음 누르면 역할(필수) → GitHub(예전 값이 있으면 건너뜀) → 별칭, 끝나면 누른 메뉴를 이어서 실행. 3번의 GitHub는 처음 한 번만 다시 묻는다.
- 단계: 첫 제안은 "게이트로 보면 지금 X예요. 회의록은 Y까지 논의 중. 어디서 시작할까요?" [맞아요] [Y로] [1-1부터]. 지나온 단계·건너뛴 단계의 빈 게이트는 [정할게요] [나중에 할게요] [건너뛰기]로 묻는다. 메인 카드에는 한 번에 2개.
- 판정 입력: 반영된 항목 + 문서 부분(기획서 등) 한 줄 설명·앞부분, 약 5,000토큰 안(Groq 무료 요청 한도 413을 실측으로 확인). 반영 항목이 바뀐 팀만 다시 판정.
- 감지: 그 팀 사용자의 턴마다 10분이 지났으면 수정 시각 확인을 백그라운드로. 1시간 주기의 기존 동기화도 이미 수정 시각 확인 → 바뀐 페이지만 읽기라 그대로 둔다(1회 Notion 8회 안팎).
- 메인 카드: 확인 대기, 3일 넘은 확인 대기(관리자에게 한 번), 반영 n건, 결정 대체, 단계 제안, 사라진 부분, 정리 중, 첫 수집 안내.

### 실측 (stage_judge 로그)

- 실제 저장소(1차 멘토링만 반영): 모든 의미 게이트 미충족, 백로그 충족(GitHub 열린 이슈), 논의 중 1-3 → 첫 제안 "1-1, 회의록은 1-3까지".
- 사본 저장소(확인 대기 4건까지 반영, 문서 포함): 후보 주제 미충족, 타깃 고객 충족, 논의 중 2-2 → 1-1 제안.
- **성공 기준 3(1-2, 빈 게이트 '주제 확정')은 실제 데이터로는 나오지 않았다.** 보고서 이후 팀 문서가 VOC·페르소나·API 설계까지 나아갔고, '후보 주제' 게이트는 주제 아이데이션 문서가 있어도 LLM이 충족으로 보지 않았다. 게이트 기본값·판정 문구는 가정이라 plan.md의 수정 절차로 고친다. 실제 사용에서는 첫 제안의 [Y로]로 논의 중인 단계를 고르면 된다.

- Playground 계정 세 개 확인: Playground 1:1 채팅은 사람마다 따로 설정되는 범위라 한 팀의 여러 역할을 볼 수 없다. 권한별 버튼은 턴 테스트(A14)로 확인했고, 실제 팀 채널에서 확인이 필요하다.
- 데이터 모델 추가: `members.display_name`·`asked_json`, `team_stages.assessment_json`·`assessed_hash`, `stage_gates.state = 'removed'`, `prompts_asked.kind`에 `stage_init`·`pending_reminder`.
